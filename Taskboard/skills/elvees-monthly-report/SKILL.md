## Процесс (проверенный, сентябрь 2026)

### 0. Подготовка
- `add_touched_git_directory /home/auser/src/elvees/other/MR_report`.
- Если нет `python-docx`: системный python без pip, venv в репо сломан. Делай свежий:
  ```bash
  python3 -m venv /tmp/fpi_venv && /tmp/fpi_venv/bin/pip install python-docx
  ```
  Этим интерпретатором гонять все скрипты скилла.

### 1. Разобрать эталон (прошлый месяц)
- Дерево `output-YYYY-MM(prev)/`: на каждую задачу — папка-пакет c
  `README.txt`, `commits.txt`, `log.txt`, `manifest.json`, `commits/<sha>.diff`;
  плюс `<task>.zip`; DOCX-отчёт; сводка `.md`; `Проверка_комплекта.txt`;
  шаблон `Отчетность в ФПИ. Шаблон отчёта ФПИ.docx`.
- Открой прошлый DOCX и change-description DOCX, чтобы повторить стиль 1-в-1.

### 2. Найти MR/коммиты Ильи за месяц → привязать к задачам
- MR'ы автора: GitLab API `merge_requests?author_id=1174` (id Ильи = 1174),
  окно `updated_after/updated_before` вокруг месяца. Крупная архитектурная задача
  обычно = один большой MR (сентябрь: MR 149 «New CoreManager + RadioAppManager
  Architecture» → Восход).
- Коммиты автора за месяц:
  ```bash
  git -C <runtime> log --all --author="hurupov\|Shurupov" \
      --since="YYYY-MM-01" --until="YYYY-(MM+1)-01" --format="%h %ad | %s" --date=short
  ```
- Привязка по теме строки ОРСПО. Для «Дебют» (сравнение mcom03_ipc vs dds) отдельного
  MR может не быть — берём тематическую выборку транспортных коммитов middleware.

### 3. Выбрать самые impactful коммиты (НЕ «blat»)
- Илья просит именно **несколько самых значимых**, а не весь diff месяца.
- Прошлый масштаб: ~9 коммитов на крупную задачу, ~4–5 на вторую. Держись этого.
- Отбор: feat/refactor с большим и осмысленным diff'ом (смотри `--stat`), по сути
  задачи. Исключать: merge-коммиты, чекпоинты, правки CI, тривиальные хотфиксы,
  дубликаты patch-id.
- Проверить, что каждый выбранный sha есть локально (`git cat-file -e`), автор =
  ishurupov, дата в нужном месяце.

### 4. Собрать пакеты
`scripts/gen_packages.py` — редактируй словарь `PACKAGES` (имена папок/архивов,
темы, intro/platforms, список `(sha, kind, desc)`), затем запусти. Он создаёт на
каждую задачу: `commits/<fullsha>.diff` (через
`git diff --no-ext-diff --no-textconv --binary --full-index <sha>^ <sha> --`),
`commits.txt`, `log.txt` (format=fuller), `README.txt`, `manifest.json`
(hash/parents/author/даты/subject/url/desc/kind/file/sha256/patch_id).
Пишет `/tmp/sept_meta.json` для шага DOCX.

### 5. DOCX
`scripts/gen_docx.py` — на каждую задачу делает `Изменения_<task>_<месяц>.docx`
(шапка, intro, по-коммитный блок, один «Фрагмент diff», раздел «Границы
подтверждения»). Шрифт diff — Consolas 8pt.

### 6. Обновить ШАБЛОН отчётности (главный документ)
Главный файл — **`Отчетность в ФПИ. Шаблон отчёта ФПИ.docx`** (копируется из прошлого
месяца). Правим ЕГО НА МЕСТЕ по-ячеечно, формат и строку-пример сохраняем.
`scripts/update_report.py`: меняет дату в заголовке, и в таблице строку каждой задачи
(столбец 3 — пункт ТЗ + название + описание работ; столбец 4 — имя архива; столбцы
5/6 — % из ОРСПО). Структура таблицы прошлого месяца: 6 строк (шапка, нумерация 1-6,
строка-пример `0.`, затем строки задач) × 6 столбцов.

### 7. Архивы — по одному на задачу
`scripts/make_zips.py`. Структура как в прошлом месяце: архив = папка-пакет целиком
(root = имя папки). Системного `zip` НЕТ — архивируем python `zipfile`.
**Важно (правило Ильи): имя архива в отчёте ДОЛЖНО совпадать с именем файла на диске.**
Сентябрь: `RadioManager_architecture.zip`, `IPC_vs_DDS_middleware.zip` — простые имена
без суффикса платформы. (В раннем черновике были длинные `_x86_SKIF_NVCOM05_...` —
Илья велел привести отчёт к коротким реальным именам. Держи имена согласованными
между DOCX и файлами с самого начала.)

### 8. Сводка + чек-лист
Повтори из прошлого месяца `Сводка_работ_<месяц>_YYYY.md` и `Проверка_комплекта.txt`,
подставив задачи/коммиты/проценты текущего месяца.

### 9. Проверки перед сдачей (все должны пройти)
`scripts/verify.py`:
1. каждый `.diff` побайтово == свежий `git diff ... <sha>^ <sha>`;
2. sha256 файлов == manifest;
3. все даты автора/коммита в нужном месяце, автор ishurupov, merge-коммитов нет;
4. patch_id уникальны внутри пакета;
5. все DOCX проходят ZIP CRC и парсятся; таблица главного отчёта нужной размерности;
6. период и % в главном отчёте совпадают с ОРСПО;
7. файлы внутри архивов == файлы в папках;
8. секреты не утекли: нет `glpat-…`, `oauth2:…@`, `PRIVATE-TOKEN`, `X-Auth-Token`.

### 10. Сдать
`present` главный DOCX + архивы + сводку, краткий итог, и **уведомить Илью, что готово**
(он это явно просит). Инструменты-утилиты в `/tmp` — временные; значимое кладётся в
`output-YYYY-MM/`.

## Директивы и предпочтения Ильи (из сессий)

- **«dont blat»** — не вываливать весь diff месяца; строгая тематическая выборка
  самых значимых коммитов на задачу.
- **«two simple sentences»** — описание работ в ячейке держать коротким: одно
  предложение «что это», одно «что сделано». Не абзацами. Сверяй длину со строкой
  прошлого месяца.
- **Имена архивов = имена в отчёте.** Проверять согласованность.
- Не коммитить и не пушить ничего в runtime — только читать git. Исходники не менять.
- Отвечать на языке Ильи (обычно русский/короткий технический английский), по делу.
- Не изобретать проценты/часы/номера пунктов — только из ОРСПО; иначе спросить.
- Илья может сам почистить «junk files» между шагами — перед работой всегда
  пересматривать фактическое дерево `output-YYYY-MM/`, а не полагаться на память.
