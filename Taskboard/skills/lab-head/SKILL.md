# Начальник лаборатории (ОРСПО, Восход)

Скилл про людей и отчётность, а не про код. Три повторяющиеся задачи: **ежемесячный план-факт**,
**отчёт в ФПИ**, **таблицы и оценки по сотрудникам**. Общая часть — сбор фактуры из Jira, GitLab и
Confluence.

## Окружение

Всё, что ходит в корпоративные сервисы, выполняется **на удалённом хосте** — с локальной машины
сети нет:

```bash
ssh supermarket-wm '...'          # основной путь; при недоступности — unitload-pc
```

Токены на хосте (никогда не вставлять в текст команды, читать из файла):
`~/jira.token`, `~/git.token`, `~/confluence.token`, `~/jenkins.token`.

Отчётные файлы лежат **локально**: `~/work/elvees/reports/<месяц>/`, `~/work/claude/lab/`.
На хосте нет pip и модуля `requests` — использовать `urllib` (или заглушку `~/pyshim`,
запуск `PYTHONPATH=$HOME/pyshim python3 ...`).

**Скрипты запускать через scp + ssh, не через heredoc:** конструкции вида
`ssh host 'cat > f <<EOF ... EOF'` ломают строки с `>=` и кавычками. Правильно:
`scp script.py supermarket-wm:~/ && ssh supermarket-wm 'python3 ~/script.py'`.

## Состав лабораторий

Логины Jira, id GitLab и роли — в `references/people.md`. Проверять актуальность по отчёту:
в файле план-факта **видимые (нескрытые) строки = свой состав**, остальные скрыты (`hidden="1"`).
Это самый надёжный источник списка людей.

## 1. Ежемесячный план-факт ОРСПО

Файл `~/work/elvees/reports/<месяц>/Отчёт <месяц> 2026 ОРСПО_Мотин Н.А.XLSX`, два листа:
`ОТЧЁТ_<МЕСЯЦ>` и `ПЛАН_<СЛЕД.МЕСЯЦ>`. Заполняются **только строки своей лаборатории**.

- Факт: `M` — распределение задач, `N` — результат выполнения. **Проценты в шкале 0–100**, не 0–1.
  Формула `P` = `(K-O)*D*M/100`.
- План: `I` — доля времени человека между проектами, в сумме по человеку = 1.
- Источник долей Восход/Дебют — `Плановые часы 2026 для Голубева.xlsx`, лист текущего месяца.
- Задачи Дебюта можно переносить из прошлого месяца, скорректировав процент.

**Редактировать xlsx только правкой XML внутри zip**, не openpyxl: в файле есть
`xl/drawings/*` и текстовые поля, которые openpyxl потеряет. После правки удалить
`xl/calcChain.xml` (и его rel + override в `[Content_Types].xml`), в `<calcPr>` добавить
`fullCalcOnLoad="1"`. Осторожно с shared-формулами (`<f t="shared" ref= si=>`): перезапись
мастер-ячейки ломает всю группу — сначала развернуть группу в явные формулы.

Проверка результата — конвертация через LibreOffice. Учесть: для обычных формул LO отдаёт
**закешированное** `<v>`; чтобы увидеть реальный пересчёт, удалить `<v>` из проверяемых ячеек.

Подробности и грабли: память `monthly_report_orspo`.

## 2. Отчёт в ФПИ

Личный отчёт = таблица docx (строка на задачу «Восход» из план-факта) + папка материалов.
Собирается на основе прошлого месяца — клонированием `<w:tr>` из старого docx, чтобы сохранить
стили. Срок — до 4 числа.

Ключевое: **ревью искать не через reportcomposer** (он смотрит на assignee/reviewer и врёт), а
через журнал событий GitLab — `GET /users/<id>/events?after=&before=`, действия `commented on`,
`approved`, `accepted`. У событий-заметок номер MR лежит в `note.noteable_iid`, а не в
`target_iid`. Ревью выходит далеко за группу `dis/sunrise`.

Материалы по коду за период — `git diff` между граничными коммитами плюс
`git log --all --author= --after= --until=`; в имени файла указывать платформу.

Подробности: память `fpi_personal_report`.

## 3. Таблица «Загрузка сотрудников» (форма НТО-8)

Форма-образец: `~/work/claude/lab/Загрузка сотрудников НТО-8(1).xlsx`. Правила заполнения,
словарь формулировок и готовые примеры — `references/staff-table.md`.

Коротко: строка 2 — шапка, строка 3 — нумерация колонок, данные с строки 4. Колонки
B..H: подразделение, должность, ФИО, функции, проекты (вовлеченность), комментарии,
квалификация. Стиль берётся копированием `_style` из строки 4, файл простой — openpyxl безопасен.

## 4. Метрики и оценка сотрудников

Скрипт `scripts/lab_metrics.py` собирает по каждому человеку:

- **Jira**: закрыто задач за период, медиана цикла «создана → resolution», сколько задач открыто
  и сколько из них старше 120 дней;
- **GitLab**: коммиты по списку репозиториев (сопоставление по `author_email`, не по имени —
  имена в коммитах бывают латиницей), merge request открытые/влитые, медиана времени до влития;
- **ревью**: комментарии к чужому коду, approve, merge (из журнала событий).

```bash
scp ~/.codex/skills/lab-head/scripts/lab_metrics.py supermarket-wm:~/
ssh supermarket-wm 'python3 ~/lab_metrics.py --since 2026-01-01 --out ~/metrics.json'
```

Выполняется ~10 минут (обход репозиториев постранично). Список людей и репозиториев — в
`references/people.md`, при необходимости передать свой через `--people` / `--projects`.

### Как интерпретировать

Цифры — опора, а не приговор. Обязательные поправки, иначе оценка будет неверной:

- **Тестировщики, тимлиды и стендовые инженеры не видны в git.** Отсутствие коммитов у
  тестировщика или начальника лаборатории — норма. Если результат человека нигде не
  фиксируется, вывод не «плохо работает», а «работу не видно, нужна фиксация результата».
- **Объём коммитов ≠ ценность.** Правка CI и алгоритм ЦОС весят одинаково.
- **Неполный охват репозиториев занижает людей**, работающих вне основного контура
  (nvcom05, sbl, no-os, civil-radio-station). Прежде чем делать вывод по низким цифрам —
  проверить, все ли его репозитории попали в обход.
- **Импорты чужого кода раздувают счётчик** (btstack, linux-stable, no-os от Analog Devices).
  Смотреть не только количество, но и репозитории.
- **Медиана цикла прячет хвост.** Если у человека большинство задач мелкие, медиана будет
  хорошей при двух задачах по полгода — смотреть максимум и «старые» задачи.
- Лучший одиночный индикатор доведённой до конца работы — **влитые MR**, а вклада в команду —
  **замечания к чужому коду**.

### Формат честной оценки

Внутренний документ (не для руководства и не для сотрудников): таблица метрик → разбор по
людям → решения. Разделы, которые себя оправдали: кого повышать, кого удерживать особыми
условиями (**bus factor = 1** — отдельный и главный раздел), крепкая середина, кто не
измеряется git'ом, аутсайдеры, отдельно — самооценка руководителя. В конце — таблица
«решение → кто → обоснование».

Правила: каждое утверждение подпирается цифрой; для кандидатов на сокращение указывать
смягчающие обстоятельства, если они есть; вместо немедленного увольнения предлагать
испытательный срок с контрольными точками, если тема объективно тяжёлая. Концентрация знаний
на одном человеке — риск больший, чем слабый сотрудник.

## Тон документов

**Для руководства** (таблицы, план-факт, ФПИ): общие формулировки, без номеров задач Jira и
названий репозиториев, без оценочных суперлативов («сильнейший», «самая сложная часть»).
Различие в уровне сотрудников передавать фактами: уровень (Senior/Middle/Junior),
самостоятельность, переходящие задачи, необходимость сопровождения.

**Для себя**: прямо, с цифрами, без смягчения.

**Никогда не упоминать AI-агента, Claude, Codex или OpenAI** — ни в коммитах, ни в MR, ни в
Jira, ни в Confluence, ни в отчётах (память `no-claude-mentions-public`).

Мигрированная память находится в `/home/nmotin/work/claude/.codex/memory/`. Сначала читать
`MEMORY.md`, затем только карточки, относящиеся к текущей задаче.

## Чего не делать

- Не выдумывать штатные наименования подразделений и лабораторий. Если официального названия
  нет в доступных источниках (оргструктура на Confluence — картинка, текст не извлекается) —
  писать сокращение отдела и явно сообщить об этом пользователю.
- Не подменять ФИО из учётной системы своим вариантом молча — расхождение показать.
- Не переносить в документ для руководства сведения об отсутствиях, больничных и отпусках
  без прямой просьбы.
- Не делать выводов о сокращении по одному источнику данных.
