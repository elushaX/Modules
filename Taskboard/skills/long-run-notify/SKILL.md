# Долгие задачи и уведомления по почте

> Локальное правило для этого ПК: не использовать этот skill и не запускать здесь его
> исполнителей, сторожей или почтовые уведомления. Пользователь явно запретил это 20.08.2026.

Задача скилла — довести долгий процесс до конца без участия сессии Claude и честно
сообщить владельцу результат. Две независимые части: **исполнитель** (сама работа
на сборочном хосте) и **сторож** (следит и шлёт письмо). Их разносят по разным
хостам, чтобы падение одного не унесло другой.

Топология в этом окружении:

```
локальный компьютер   → nmotin@supermarket-wm → zeld-lpor-nmotin
   (сессия Codex)          сторож+почта          исполнитель
   умирает с сессией       живёт всегда          живёт всегда
```

Ничего из этого нельзя запускать на локальном компьютере: сессия закроется и
процесс умрёт. По той же причине **MCP-сервер `ews` не годится для отложенных
уведомлений** — он работает в сессии. Для писем из сессии он удобен, для сторожа —
нет; сторожу нужен `smtplib` прямо на удалённом хосте.

## 1. Исполнитель: скрипт-цепочка

Долгую работу оформляют отдельным скриптом на сборочном хосте, а не серией команд
из сессии. Обязательные свойства (готовый шаблон — `references/chain-template.sh`):

- `set -Eeuo pipefail` и явный `export` всех переменных окружения, которые
  подхватывает сборка: то, что было в вашем интерактивном `ssh`, в detached-процессе
  не появится само;
- **маркер завершения в логе** — последняя строка вида `ВСЁ ГОТОВО rc=0`. Это
  единственный надёжный признак конца, см. п. 3;
- временны́е метки перед каждой стадией: по ним потом видно, где встало;
- запуск detached: `setsid nohup ./chain.sh > /tmp/logs/chain-run.log 2>&1 < /dev/null &`.
  Без `setsid`/`nohup` процесс уедет вместе с ssh-сессией.

## 2. Сторож: скрипт уведомления

Шаблон — `references/notify-template.py`. Ставится на `supermarket-wm`, запускается
так же detached. Обязательные свойства:

- **сначала записать итог в файл, потом слать письмо.** Почта может отказать
  (пароль сменился, релей лёг) — результат не должен пропасть. Файл-флаг вроде
  `~/<задача>-READY.txt` читается позже без всякой почты;
- **недоступность хоста ≠ конец задачи.** ssh с `rc=255` означает «не знаю», а не
  «готово». Считать подряд идущие неудачи и писать отдельное письмо «хост
  недоступен» после ~часа;
- дедлайн (`GIVE_UP_HOURS`) с отдельной темой письма, чтобы молчание не путали с успехом;
- в письмо — пути к артефактам, `ls -la` по ним и хвост лога. Владелец должен
  понять исход, не заходя на хост;
- перед запуском проверить, что сторож один: `pgrep -af '<имя>[.]py'`. Второй
  экземпляр — это дубли писем.

Опрос раз в 60–120 с; чаще незачем, ssh-коннект на каждый опрос не бесплатный.

## 3. Как определять, что задача закончилась

**Правильно — по маркеру результата**, а не по наличию процесса:

```bash
tail -3 /tmp/logs/chain-run.log | grep -q 'ВСЁ ГОТОВО rc=0'
```

Ожидание по имени процесса ломается, и ломалось на практике. `pgrep -f chain.sh`
совпадает с собственной командной строкой вызывающего — отсюда цикл
`until ! pgrep -f chain.sh; do sleep 60; done`, который висит вечно. Скобки
(`pgrep -f "chain[.]sh"`) лечат самосовпадение, **но не спасают от чужого
наблюдателя**: любой посторонний процесс, у которого в командной строке есть слово
`chain.sh`, будет засчитан за работающую сборку. 07.08.2026 именно так осиротевший
цикл от убитой фоновой задачи заставил сторожа проспать успешную сборку и прислать
через 12 часов «не дождался» вместо «готово».

Отсюда правило: **убирайте за собой свои временные наблюдатели**. Фоновые задачи
сессии (`run_in_background`, циклы ожидания) не умирают вместе с сессией — перед
уходом их надо явно погасить и проверить `ps -p <pid>`.

Если маркера в логе нет и добавить его нельзя, годятся: файл-флаг, который пишет
сама задача; появление артефакта нужного размера; `wait` по конкретному pid,
записанному в pidfile при старте. Имя процесса — в последнюю очередь.

## 4. Почта: owa.elvees.com

Детали канала и его грабли вынесены в память `smtp_notify_supermarket.md`.
Кратко, чтобы не искать:

- `owa.elvees.com` открыт с `supermarket-wm` на портах 25 и 587;
- **анонимная отправка запрещена** — на 25-м приходит
  `530 5.7.57 Client was not authenticated to send anonymous mail during MAIL FROM`.
  Нужен 587 + `starttls()` + `login()`;
- логин — полный адрес `nmotin@elvees.com`;
- хватает stdlib `smtplib`; на хосте нет ни pip, ни `requests`.

**Получатель по умолчанию — только `nmotin@elvees.com`.** Личные и посторонние
адреса в список не добавлять, даже «для проверки», без прямой просьбы.

## 5. Пароль

Пароль кладёт владелец, своими руками:

```bash
ssh -t nmotin@supermarket-wm 'read -rs -p "пароль: " p; echo; (umask 077; printf "%s\n" "$p" > ~/.buildalt-smtp); unset p'
```

- `umask 077` вместо `chmod 600` после записи: иначе файл на мгновение существует с 644;
- **это не работает из сессии Codex** — запуск агента не даёт настоящего tty
  (`Pseudo-terminal will not be allocated because stdin is not a terminal`), `read`
  получает EOF и в файл уходит один перевод строки. Признак — `wc -c` даёт 1.
  Просить владельца выполнить команду в своём терминале;
- проверять файл только косвенно: `wc -c` и `stat -c %a`. Содержимое не читать и
  нигде не печатать;
- пароль из чужих хранилищ (`credentials.json` от EWS-MCP и т.п.) не брать и по ssh
  не передавать.

При `535 5.7.3 Authentication unsuccessful` **перебирать форматы логина вслепую
нельзя** — в AD блокировка учётной записи после нескольких неудач. Сообщить
владельцу и дать ему исправить пароль.

## 6. Проверка канала до того, как он понадобится

Сторож, который выяснит, что почта не работает, через 8 часов — бесполезен.
Порядок:

1. развернуть сторожа;
2. **его же функцией `send()`** отправить тестовое письмо (не отдельным скриптом —
   иначе проверите не тот код);
3. убедиться в логе сторожа: `письмо отправлено: nmotin@elvees.com`;
4. только потом запускать в режиме ожидания и убеждаться, что экземпляр один.

## 7. Отчёт владельцу при передаче

Когда владелец уходит, в последнем сообщении должно быть: что именно продолжает
работать и где; куда лягут артефакты (полные пути); как проверить руками; куда
придёт письмо; что делать, если письма нет (файл-флаг, лог сторожа
`~/<задача>-notify.state`).

## Чего не делать

- Не запускать сторожа или задачу на локальном компьютере, если владелец
  собирается закрыть сессию.
- Не считать «процесс не найден» за «успешно завершилось» — проверять именно
  успешность (`rc=0`, маркер), иначе упавшая сборка придёт письмом «готово».
- Не читать логи с прогресс-барами напрямую: там `\r` вместо `\n`.
  `tr '\r' '\n' < log | tail -20`, и `grep -a` — логи сборки часто не текстовые.
- Не оставлять после себя фоновые циклы ожидания.
- Не слать письмо на каждый шаг: одно письмо на исход, максимум плюс одно
  аварийное.
